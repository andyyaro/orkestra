## Journeys

### newbie
I installed orkestra-runtime 0.4.1 fresh via uv, ran `orkestra demo` (worked exactly as advertised — the rejection/repair loop is visible and easy to understand), then followed the README's "Use it on your project" path: `orkestra start` in an empty directory, `orkestra run`, `orkestra review`, `orkestra accept`. The end-to-end practice-mode lifecycle completed successfully and cleanly merged into main with a clear commit trail — the core promise held up. However, the interactive `start` wizard has a real bug in the spec-description prompt that made me think the tool had hung or was broken (it silently re-prompts several times, deterministically, before proceeding, for reasons I could not determine even with identical repeated inputs), and the tool over-claims "verification passed" / "passed your acceptance commands" in `run`/`review`/`accept` output even when zero verification commands were configured — that phrasing will mislead a beginner who skipped the (optional, blank-to-skip) test-command prompt into thinking their SPEC.md's acceptance criteria were actually checked. I also hit a copy-paste-able but broken fix suggestion: `orkestra watch` failed because the TUI extra wasn't installed, but the fix command it printed was the exact same install command that produced the broken state, and the `--help` listing for `watch` has a template bug that omits the extra's name entirely. None of this blocked me from finishing the tutorial (there's a working `--non-interactive` escape hatch), but a true first-timer relying only on the interactive path — the one the README's grammar implies is normal — would very plausibly bail out at the bare "Aborted." wall with zero explanation of what went wrong or why to fix it.

Praise: `orkestra demo` matches the README's advertised transcript almost verbatim, runs in seconds, needs no login/tokens, and clearly demonstrates the rejection-then-repair loop that is the product's core pitch. · `orkestra start --non-interactive` is a clean, reliable escape hatch: it auto-creates a git repo, auto-detects that no real agent CLIs are signed in and falls back to practice mode with a clear explanation, and prints exactly what to do next (git add/commit, then `orkestra run`). · `orkestra doctor` gives a genuinely useful at-a-glance readiness table (git, worktrees, repo, config, each agent, docker) that would help debug a real setup fast. · The full run -> review -> accept lifecycle produces a legible, inspectable git history (per-task commits, integration commits, a final 'Accept orkestra run ...' commit) and never touched files outside what it said it would. · `orkestra accept` asks for explicit y/N confirmation before touching the branch, exactly as the README promises ('asks before touching anything').

### dirty-repo
Installed orkestra-runtime 0.4.1 cleanly via uv in an isolated PATH sandbox with fake agents. Built a 4-commit Python repo, then dirtied it with an unstaged tracked-file edit, a staged tracked-file edit, and an untracked scratch file. `ORK start . --non-interactive` correctly detected the dirty tree, refused to touch anything, exited 1, and printed a clear, actionable error with two remediation options (commit-all or stash). Verified byte-for-byte that git status, git diff (unstaged and staged), the file tree, and the commit log were all identical before and after the failed attempt — no mutation whatsoever, which is exactly the safety guarantee a user would want from an orchestration tool touching their working tree. Followed the error's first suggested command (`git add -A && git commit`) literally, and the retry of `orkestra start` then succeeded, entering practice mode with two fake agents since no real CLIs were on PATH, writing `.orkestra/config.toml` and `SPEC.md`, and committing only those setup files as promised. The full downstream journey — `run` (3/3 tasks completed by fake agents, verified and reviewed), `review` (clean summary of the diff and commits), and `accept --yes` (folded the verified result into main) — worked without any errors or dead ends; note `accept` requires `--yes` for non-interactive use since it defaults to an interactive y/N prompt that aborts under piped/no-tty conditions, which is reasonable but worth knowing. Finally, dirtying the now-clean repo again (tracked-file edit + new untracked file) and running `orkestra run` directly reproduced the same safe refusal behavior (exit 1, zero mutation), confirming the dirty-tree guard is consistently enforced across entry points. Overall this is a genuinely solid first-run experience: the safety guarantees held up under adversarial byte-level verification, the practice-mode fallback for missing agent CLIs is a thoughtful touch, and the guided happy path (start → run → review → accept) worked end-to-end with no crashes, hangs, or confusing states. The only friction was minor: `run`'s dirty-tree error is less helpful than `start`'s (no example commands), and the suggested `git add -A` remediation silently commits untracked scratch files without warning the user of that side effect.

Praise: Dirty-tree detection in both `start` and `run` is byte-for-byte non-mutating — verified via diff of git status/diff/staged-diff/file-tree/log before and after the failed command, all identical · The `start` error message is genuinely excellent UX: explains why it can't proceed, offers two concrete remediation paths (commit or stash), and following it literally led straight to success on retry · Practice mode with fake agents kicks in automatically when fewer than two real agent CLIs are found, with a clear one-line explanation, letting a new user complete the whole lifecycle without any setup · The full start -> run -> review -> accept pipeline worked end-to-end on the first try with clear, well-formatted progress output and a sensible final summary (task table, verification/review status, next-step hints) · Consistent, well-formatted 'next steps' hints after every command (start suggests run, run suggests review/accept, etc.) made the guided journey easy to follow without consulting docs
