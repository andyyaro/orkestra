# Fleet Test Report #4 — v0.5.0 with real agents (2026-07-25)

6 Opus-tester personas driving orkestra-runtime==0.5.0 from PyPI with three real Sonnet identities (claude/codex/antigravity) implementing, cross-reviewing and verifying. 5 personas ran inside the workflow; conflict-provoker was re-run standalone after an API-side failure. 35 unique findings after dedupe; the top 6 were independently re-verified.

**Headline: a critical regression in 0.5.0 itself.** `git add -A -- . :(exclude)__pycache__ …` (added in 0.5.0 to keep build artifacts out of commits) makes git hard-fail whenever those paths are ignored — including by the `.gitignore` `orkestra init` writes. Every task in such a repo failed to stage its work. Fixed in v0.5.1.

**The 0.5.0 corrections that were exercised all HELD**: [verify] authority, plan-acceptance validation and dropping, pre-flight blocking with zero agent dispatch, failure output capture (with agents visibly repairing from it), usage accounting incl. planning/probes, and — proven by conflict-provoker — merge-conflict recovery with zero lost work.

## Journeys, usage and per-change verdicts

### verification-truth
I seeded a Python repo with a committed empty `stats.py`, a frozen 11-test unittest suite I wrote myself, and a SPEC forbidding edits to `tests/`, with `[verify] commands = ["python3 -m unittest discover -q -s tests"]`. `orkestra run` spent 7m15s in analysis/probe/plan/challenge before the first task appeared, then produced a 3-task plan (research "extract-test-contract", review "review-test-contract", implement "implement-stats-module") for what is a single-file, 25-line job. The flagship question — does the repair loop work now that failure output reaches the agent — answers YES: the research task's attempt 1 failed `[verify]` at 18:24:50 with the full unittest traceback captured verbatim in the event row (`AttributeError: module 'stats' has no attribute 'median'` plus per-test tracebacks), and attempt 2 by a different agent passed at 18:25:39; the same fail→fix→pass cycle repeated for the review task (18:27:52 FAIL → 18:34:24 PASS). My `[verify]` command demonstrably ran on every task, and three `ignoring plan acceptance entry` warnings fired with genuinely useful reasons ("contains shell/prose syntax", "'The' is not an executable on PATH"). Then the run hit a wall: every single task's `git add -A -- . :(exclude)__pycache__ ...` staging step exits 1 because `.gitignore` — the one `orkestra init` itself wrote — ignores `__pycache__`, which the agents create merely by running the tests Orkestra told them to run. The implement task blocked three times on this; `retry` is offered as the fix and provably cannot work because every retry re-runs the tests and every worktree is pinned to the original base commit, so even fixing `.gitignore` on main doesn't help (I tried). Worse, for the research and review tasks the same failure did not block — their workspaces are recorded as state `lost`, their work (a CONTRACT.md) was silently discarded, their independent review was skipped as "task produced no repository changes to review", and they were marked **done**. Final tally after ~45 minutes wall clock, 18 agent calls, 6,055,580 cached input tokens, 107,763 output tokens and **$5.58**: `orkestra review` reports "result: 0 commit(s)", the integration branch is identical to the base commit, and `orkestra accept` refuses. The end product quality is a paradox — I fished the abandoned worktree's `stats.py` out by hand and it is *perfect* (11/11 tests pass, `tests/` provably untouched by `git diff`, correct even-length median and smallest-on-tie mode), so the agents did the job flawlessly and Orkestra threw the result away. As shipped, 0.5.0 cannot complete a single task in any Python repo it initializes itself.
